# 日常运营与冷启动

## 从零形成方向

用户未确定人设，不代其宣称多年 NAS 经验或真实生活经历。提供可测试的方向：

| 方向 | 内容重点 | 证据需求 |
| --- | --- | --- |
| NAS 实用教程 | 接入已有照片、找回某张照片 | 当前文档、操作与界面 |
| 开发者分享 | 为什么做某功能、解决什么问题 | 用户提供的动机或开发记录 |
| 生活记录/plog | 旅行回顾、城市足迹、仪式感 | 获准公开的照片与经历；否则标注示例 |

需要冷启动方案时，可先建议两周、每周三篇作为可调整的试验节奏，不当作平台算法要求。多数内容面向 NAS，留少量内容探索摄影和旅行人群。根据制作能力调整频次。

## 选题和排期

按需给出选题表：受众、场景、角度、平台、所需素材、行动引导、计划日期、待验证假设。选题必须落到当前产品能力，避免仅用“宝藏神器”等空泛标题。

- 教程：注明版本、前置条件和操作结果；未测试的步骤不称为实测。“一键”“几分钟”必须有依据。
- 热点：核对事件时间与来源，说明与照片管理或回忆记录的关联；关联弱时用常青选题。
- 用户故事：使用用户提供或获准引用的素材，分清原话、改写与示例。缺少素材可做采访提纲或示例故事。
- 竞品比较：按同一用户任务、版本、部署条件比较，引用对方官方资料并标明日期；未知写未知。解释适合谁，不臆造短板或全面替代承诺。
- 社区互动：可做问题回复草稿和讨论题，不默认代发或批量触达。

## 曝光与 Star 复盘

每条内容选择一个主要行动：看演示、收藏教程、讨论需求或访问仓库。技术受众内容可自然邀请“觉得有用，欢迎在 GitHub 点个 Star 支持”；不制造利益交换或虚假热度。引流遵循当次核验的平台规则，不提供规避审核方案。

只分析实际可得数据：发布链接与时间、方向、曝光/阅读、收藏、评论、分享、可观测的站点或仓库访问，以及同期 Star 变化。缺失数据写未提供，不补零。

同平台尽量比较相同观察窗口，收藏率等指标明确分母；跨平台口径不同则分开比较。发布前后 Star 增量只是同期变化，无归因证据时不能全归于某篇帖子。

输出“观察 → 可能原因 → 下一次试验”，一次优先调整一个主要因素，如封面角度或受众。小样本结论标为初步信号；没有数据时交记录字段和试验计划，不伪造复盘结果。
