# FFmpeg 媒体处理评估

评估日期：2026-10-03。此次评估没有替换生产缩略图逻辑，也没有覆盖既有缩略图或原始素材。

## 当前实现

- `storage.py`：照片使用 Pillow 输出 1440 长边预览和 250 长边缩略图，默认 WebP 质量分别为 85、80。入库任务复用同一个图像对象，继续提取元数据和颜色。
- 视频使用 OpenCV，在开头、短时偏移、四分之一和二分之一处最多取五帧，按亮度、对比度和边缘评分选优，避免黑屏后输出两种 WebP。
- `video_meta.py`：MP4/MOV 等容器使用纯 Python 解析，避免启动外部程序；非 ISO BMFF 容器覆盖较少。
- `motion_photo.py`：动态照片中的 MP4 通过字节偏移直接提取，不需要解码或转码。
- 一日一帧的裁剪、缩放、补帧、字幕叠加、拼接、MP4 编码和作品封面已使用 FFmpeg；时长探测使用 FFprobe。
- 本机使用已有 `D:\Programs\ffmpeg\bin\ffmpeg.exe`，Docker 已补依赖。桌面 sidecar 的跨平台分发仍需单独解决，不能假设所有安装都有 FFmpeg。

## 开发机器上的初步对比

使用三个真实视频和一个 JPEG；每种方式预热一次，再运行三次取中位数。所有产物写入独立临时目录，退出后清理。使用默认尺寸和质量参数，时间包括抽帧、缩放和两个 WebP 文件写入，不包括 Python 模块加载、数据库查询及任务排队。

| 视频 | 现有 OpenCV 五帧选优 | FFmpeg 单帧、双尺寸输出 | FFmpeg 分别启动五次抽帧后沿用原评分和 Pillow 输出 |
| --- | ---: | ---: | ---: |
| 16.267 秒，1920×1080 | 741 ms | 400 ms | 2005 ms |
| 3.591 秒，1080×1920 | 1221 ms | 236 ms | 1907 ms |
| 2.033 秒，1080×1440 | 658 ms | 522 ms | 2651 ms |

1260×2800 JPEG：Pillow 双尺寸输出约 240 ms；FFmpeg 解码后 split/scale/libwebp 双尺寸输出约 134 ms。

这些结果只代表开发机器上的小样本。测试时有开发服务和前端构建活动，并非隔离性能实验。FFmpeg 单帧视频路径省去了选优，不能将差值当作相同质量的加速；两套 WebP 编码器及缩放默认算法不同，相同质量数值不代表同等视觉质量。JPEG 测试也未包含入库时图像复用的收益，不能外推为整个入库任务提速。

结论：FFmpeg 可以生成缩略图，单帧路径有提速潜力；逐帧启动进程会显著抵消收益。尚不能据此整体替换现有图片或视频缩略图任务。后续应验证单进程多候选抽帧、低分辨率评分后仅输出最佳帧，并覆盖黑屏、旋转、HDR、HEIC、长视频和损坏文件。

## 适合继续交给 FFmpeg 的工作

| 工作 | 建议 | 原因与边界 |
| --- | --- | --- |
| 视频缩略图 | 做可选后端或 OpenCV 失败时的回退，保留候选帧选优 | 格式覆盖和解码能力有价值；先验证单进程采样，不能用固定帧替代现有选优而声称等价 |
| 浏览器播放兼容副本 | 优先考虑，输出 H.264/AAC MP4 并缓存，保留原文件 | 视频无法播放时转码；若编码已兼容而只是容器问题，可先尝试无重编码封装；是否兼容仍需具体浏览器与编码参数验证 |
| 非 MP4/MOV 元数据 | FFprobe 作为补充和失败回退 | 增补 MKV/WebM/AVI 的视频流、时长、尺寸和旋转信息；继续保留拍摄时间的现有墙钟语义 |
| 一日一帧生成 | 已使用，后续再评估批处理和硬件编码 | 片段逐次启动进程有优化空间；GPU 编码必须实际检查设备和驱动，不能假设更快 |
| 视频拖动预览、选帧条 | 新功能需要时使用抽帧和 tile 生成联系表 | 减少前端反复解码完整视频，输出缩略图序列或雪碧图 |
| 普通照片缩略图 | 先保留 Pillow；独立重建任务可扩大样本试验 | 入库流程共享图像对象，同时要保持 EXIF/ICC/HEIC 等行为；单张 JPEG 初测不支持全面迁移 |
| 动态照片 MP4 提取 | 保留字节提取；仅后续兼容转码交给 FFmpeg | 当前只复制嵌入的视频数据，加入解码无助于提取速度 |
| OCR、人脸识别、语义分类、文件 MD5 | 保留原流程 | FFmpeg 适合提供采样画面，不承担这些识别或文件校验任务 |

FFmpeg 的 `thumbnail` 滤镜可选取一组连续帧中具有代表性的帧，但与当前黑屏排除和边缘评分并不等价。扩大采样数量也会增加内存和解码成本。

官方资料：[thumbnail/scale/tile 滤镜](https://ffmpeg.org/ffmpeg-filters.html)、[转码与 streamcopy](https://ffmpeg.org/ffmpeg.html)、[FFprobe 元数据](https://ffmpeg.org/ffprobe.html)。FFmpeg 官方文档也指出硬件解码未必更快，GPU 到系统内存的复制可能带来额外损耗。
