# 票夹 UI 与相册关联优化需求文档

> 版本：v0.3 视觉调整记录｜日期：2026-10-06  
> 代码核对基线：本地 HEAD `8f6c6034`  
> 文档先形成优化方案；经用户授权后已实施首期 P0，实施范围与验证记录见第 13 节。第 2 节保留改造前源码现状。

## 1. 产品方向

将“车票管理”升级为“票夹”：保存一次出发、一次游览或一次观演的凭证，让用户沿着票据找回照片、相册和回忆，也能从这些内容回到票据。

独立票夹保留，承担跨相册检索和整理；相册、回忆、旅程提供带上下文的票据入口。页面主内容从交通统计与管理操作转向“票据 + 相关经历”，里程、时长等交通能力按类型呈现。

首期完整优化现有火车票、机票，补齐双向关联及移动端体验；景区门票、演唱会票、电影票作为下一阶段类型扩展，本期明确其展示和数据契约，不提供不可用的新增入口。

## 2. 现状与问题

| 源码事实 | 用户影响 | 优化要求 |
| --- | --- | --- |
| 桌面车票在“更多”，移动端在“旅程与管理”；相册首页展示相册和回忆，没有票夹分区 | 用户难以把票据视为图库内容的一部分 | 相册首页增加票夹预览与全部入口，独立导航同步改名 |
| 当前已有火车票、机票两类数据，但标题、空态和部分操作仍称“车票” | 命名与现有能力及未来扩展不一致 | 通用入口称“票夹/票据”，具体类型保留“火车票/机票” |
| 票据已有 `photo_id`，可打开原票照片；页面缺少相关相册、回忆的回访入口 | 看完一张票据后，无法继续回顾整段经历 | 区分原票图片和相关照片，增加关联摘要、详情与双向跳转 |
| 回忆服务已有 `MemoryTicket` 关联，回忆详情展示“行程票据” | 已有基础关系，但票据页未形成双向浏览闭环 | 复用已有回忆关联，补充反向查询与可点击摘要 |
| 旅程主要存在于位置轨迹、足迹和旅行整理能力中，未发现独立旅程管理路由 | 直接设计全新旅程实体会扩大本次改动 | 优先接入现有轨迹上下文，持久关系另作阶段决策 |
| 页首已经使用通用样式与部分 `ResponsiveDialog`，但火车票/机票编辑仍是自建居中弹窗，纸质票预览使用 `el-dialog` | 按钮、关闭方式、滚动和手机安全区处理不统一 | 统一组件与交互规则，保留现有全局主题体系 |
| 手机顶部依次出现统计、乘车人、筛选排序、视图、全选与删除；列表还有额外内边距 | 首屏层级偏多，票据空间被挤占 | 统计收起、筛选合并、批量操作按需出现、统一边距 |
| `TicketFrontend` 将航班号放入 `trainCode`，排序与统计围绕交通字段 | 新类型容易被迫填入不适用字段 | 建立通用摘要与类型能力契约，避免继续扩展交通专用字段 |

以上为源码判断，不将未运行浏览器的推断写作已验证的视觉缺陷。

## 3. 目标与范围

### 3.1 用户故事

| 场景 | 目标路径 | 结果 |
| --- | --- | --- |
| 浏览旅行相册 | 相册详情 → 相关票据 → 票据详情 → 返回 | 找到这次旅行的交通凭证，返回原位置 |
| 整理旧车票 | 票夹 → 某张票据 → 关联相册/回忆 | 把凭证放入已有经历，不重复创建照片或回忆 |
| 重温一次回忆 | 回忆详情 → 相关票据 → 原票图片/关联相册 | 在照片、事件和凭证之间连续浏览 |
| 查看旅程 | 位置轨迹 → 当前旅程的票据候选 → 查看/确认 | 交通信息作为补充证据，候选关系有明确提示 |
| 手机录入 | 新增 → 选择类型 → 识别或手填 → 检查 → 保存 | 输入、保存和返回均符合其他页面习惯 |
| 后续收藏电影票 | 票夹 → 电影票 → 电影名称/影院/场次 | 无须出发站、到达站和里程等交通字段 |

### 3.2 首期必须交付（P0）

- “票夹”命名、相册首页入口、相册详情和回忆详情的双向浏览。
- 票据详情、原票图片、关联相册/回忆的查看与手动关联、解除关联。
- 现有旅程上下文的票据候选入口与返回，不新建独立旅程管理系统。
- 火车票与机票的列表、时间轴、搜索筛选、新增编辑、导入导出和批量操作适配。
- 移动端布局、按钮、菜单、弹窗、主题与安全区统一。
- 为新类型预留通用摘要、类型字段、能力声明、关联契约及兼容规则。

### 3.3 后续交付（P1）

景区门票、演唱会票、电影票的手动录入和专属展示；基于时间、地点的可解释关联建议；旅程持久关联。各新类型 OCR 单独评估，不以识别能力作为手动收藏的前置条件。

本次不包含购票、支付、验票、票务订单同步、完整行程规划、新增顶层移动导航或票据关系图谱节点。首页推荐与年度总结可在关联稳定后另行设计。

## 4. 信息架构与入口

### 4.1 命名和导航

- 页面和导航名称统一为“票夹”，新增按钮为“新增票据”。详情按类型命名，例如“火车票详情”。
- 桌面从“更多”移至“探索”，与记忆、地图相邻；移动端保留“更多”中的票夹快捷入口，主要发现入口增加在相册首页。
- 首期保留 `/ticket` 路由，避免破坏书签和现有入口。后续如改为 `/tickets`，必须提供旧地址重定向。
- “统计”明确称“交通统计”；现有统计页继续服务火车票和机票，入口放在票夹更多菜单及交通类型摘要中。

### 4.2 相册首页

增加可折叠、可排序、可隐藏的“票夹”分区，沿用现有分组设置。默认放在“回忆”之后，不改变用户已保存的分组顺序。

分区展示最近 6 张票据的简洁封面卡片：类型、标题、发生日期；有原票图片时优先展示裁切预览，没有图片时使用类型图标与主题底色。卡片打开票据详情，“查看全部”打开票夹。手机沿用相册封面横向浏览，允许明确的加载更多入口。

空态展示“留下一张票据，找回一段经历”及“新增票据”；分组加载失败只影响本分组，可单独重试，不阻塞相册首页。

### 4.3 相册详情与回忆详情

新增或升级“相关票据”区域，默认放在主要照片内容之后，可折叠。显示已确认关联数量及最多 3 张紧凑卡片，“查看全部”进入带当前对象筛选的票夹。

- 相册详情允许“关联已有票据”；新增票据时携带当前相册上下文，保存成功后建立关系。
- 回忆详情复用现有票据关联，新增查看详情、关联/解除操作，标题由“行程票据”调整为“相关票据”。
- 已确认关系与推断关系分区：后者称“可能相关”，不计入已关联数量；确认或排除后刷新双方展示。
- 只有照片时间或地点相近时，不自动把票据加入相册或已确认回忆。

### 4.4 旅程与地点上下文

现有位置轨迹的当前旅程摘要增加“可能相关票据”入口，查询使用当前旅程起止时间和可用地点，展示匹配依据，如“出发日期在这段旅程内”。只按时间匹配时明确写“时间相近”。

首期候选浏览不等同于持久绑定，也不宣称用户已乘车、到访或观演。用户可打开票据后关联到承载这次经历的相册/回忆。轨迹分组可能随照片或算法变化，不用分组数组下标作为永久关系 ID。

仅有城市名称不能绘制精确站点。照片轨迹与票据交通线如后续合并，需区分“拍摄顺序”和“票据行程”，不把二者拼接为真实路线。

## 5. 票夹页面设计

### 5.1 页面层级

桌面依次为：标题与搜索/新增/更多工具栏 → 类型分类 → 当前筛选摘要 → 票据内容。宽屏侧栏可展示交通统计和关联整理入口；中小屏移入筛选面板或折叠摘要。

手机布局示意（结构线框，非最终视觉稿）：

```text
票夹                          搜索  ＋  更多
全部   交通                         筛选
全部票据 · 最新优先              切换视图
──────────────────────────────────────
6 月 12 日
火车票   北京南 → 杭州东          更多
Gxx · 09:20
关联：杭州之旅相册 · 1 段回忆
──────────────────────────────────────
6 月 10 日
机票     上海 → 成都              更多
航班号 · 18:30
尚未关联经历                    关联
```

首期分类只显示“全部、交通”，交通下筛选火车票/机票，火车票可进一步选择高铁/动车、普速。未来扩展为“全部、交通、游览、演出、电影”，不提前展示空类别或不可点击入口。

### 5.2 列表和卡片

默认使用按日期倒序的紧凑时间轴，保留卡片视图和用户选择；有历史视图偏好时优先沿用。手机时间轴单列，日期分组可粘附，不采用左右交错的大节点布局。

卡片主层级为“类型 + 核心标题 → 发生时间/车次或场次 → 关联摘要”。票价、座位、里程、时长和备注进入详情，卡片可按空间保留少量次要信息，不要求所有字段同时出现。

- 卡片主体点击打开详情；更多、关联、选择按钮有独立点击区域，避免触发详情。
- 原票图片与经历照片分开表达：原票是凭证，相关照片是回顾内容。
- 已关联摘要可跳转相册/回忆；多个对象展示少量标签与“另 N 项”，详情中展开全部。
- 未关联状态显示低强调的“关联经历”，与新增/编辑等主要操作区分。
- 长站名、航班号、场馆和活动名允许换行；摘要过长可截断，详情必须可读全文。
- 选择控件只在批量模式出现，普通浏览不常驻复选框；桌面操作同时支持 hover 和键盘焦点。

### 5.3 搜索、筛选和统计

通用筛选：类型、日期范围、关联状态、关联相册/回忆；交通附加筛选：交通子类型、乘车/乘机人。后续场馆、影片等筛选按类型提供，参与人不自动映射为照片人物。

手机将筛选、排序收进同一面板，入口显示已生效条件数量。面板含“重置、应用”，关闭不提交草稿。列表上方显示可移除条件标签和结果数量，清空条件一步可达。

默认按发生日期最新优先；票价排序通用但允许缺失，里程/时长仅交通筛选时可用。切回全部类型时，不适用的排序恢复日期并提示。没有日期或价格的票据排在有效值之后，不当作零值统计。

交通统计在手机默认折叠为一行“交通概览”，展开后查看城市、时长、里程；大数字使用紧凑展示并可读完整值。必须标注是“全部交通票据”还是“当前筛选交通票据”，本方案采用当前筛选范围；候选关系不参与已关联统计。统计计算失败不阻止票据浏览。

### 5.4 批量模式

从更多菜单进入“选择票据”，显示已选数量、退出与当前筛选结果全选。底部操作栏提供关联、导出、删除，避开安全区；沿用全局选择模式协调底部导航。

切换筛选需清空选择并提示，不能携带隐藏项目执行删除。“全选”说明选择当前筛选全部结果还是已加载项目；首期采用当前筛选全部结果，服务端分页时须先具备可可靠枚举/批量处理的能力，否则改为“选择已加载 N 项”并明确文案。

删除确认写明票据数量，以及“删除票据将解除关联，原票照片、相册和回忆保留”。批量部分失败需反馈成功/失败数量，保留失败项选择，允许重试，不能笼统显示全部完成。

## 6. 详情与关联交互

### 6.1 票据详情

桌面使用右侧详情面板；手机使用全屏详情容器，顺序如下：

1. 标题、返回、更多操作。
2. 核心票面摘要及原票图片入口。
3. 相关相册、相关回忆：已确认对象、数量、关联/解除操作。
4. 相关照片：首期为已确认相册/回忆中的照片预览，标注来源、去重并限制首屏数量；不直接复制这些照片到票据。
5. 类型专属字段、备注及可折叠的交通数据。

没有原票图片时，不生成虚构凭证。火车票保留仿真纸票作为次级“纪念票面”操作，标注其展示用途；机票和其他类型不出现火车票专属按钮。

### 6.2 关联操作

“关联经历”打开选择器，可切换相册与回忆，搜索名称、多选并显示已关联状态。相册范围首期为当前用户拥有、可编辑的普通相册，自动生成/条件相册只允许来源浏览；回忆仅允许当前用户可编辑的已确认回忆。

确认后双方入口、数量和摘要同时更新；相同对象不重复绑定。保存失败保留选择与搜索条件。解除关系仅移除关系，不删除任何实体。

一张票据可关联多个相册或回忆；一个相册/回忆可包含多张不同类型票据。人工确认与候选关系必须保留来源和状态，明确的人工排除不得被自动建议立即重新加入。

从相册或回忆进入票据再返回，应恢复原页滚动位置；从筛选列表进入详情再返回，应恢复搜索、筛选、视图和已加载范围。关联入口跨页面打开时，关闭原弹层后导航，避免返回到遗留遮罩。

### 6.3 候选关系边界

P0 读取现有推断回忆关联及旅程查询候选；P1 扩展自动建议。不把当前服务中固定的推断置信值显示为真实概率。

候选只展示可解释依据：时间重叠、可解析地点相符、来自同一原票照片等。日期缺失、城市同名、跨夜交通等情况降级为较宽候选或不推荐；不能因票面日期与照片拍摄日期不同就自动改写数据。

不要求关联某次经历才能保存票据。“票据存在”不等于“实际参与”，涉及到访、同行与真实旅程的结论仍需已有证据或人工确认。

## 7. 移动端与通用组件规范

### 7.1 布局与按钮

- 沿用现有 768px 移动/桌面分界；页面使用 `--ts-page-gutter`、通用标题、surface、工具栏与间距变量，移除重复内容内边距。
- 页首主要操作保留搜索、新增、更多；导入、导出和统计进入更多菜单。以相册现有工具栏的顺序、大小、玻璃样式和反馈为基准。
- 点击热区至少 44×44 CSS px；较小图标通过外层热区满足要求，相邻点击区不重叠。图标操作具备可读名称，状态具有 loading/disabled/焦点反馈。
- 使用 `ts-button`、`IconButton`、`BackButton` 等通用组件或工具类；危险色用于删除，不把编辑、预览等普通操作做成多种高饱和色按钮。
- 不新增悬浮加号与页首新增的重复入口；票据多时以列表可读性为优先。

### 7.2 菜单与弹窗

| 操作 | 手机 | 桌面 | 通用规则 |
| --- | --- | --- | --- |
| 页首更多、单票更多 | `AdaptiveMenu` 小型 popover，与相册工具栏一致 | 锚定菜单 | 操作过多时分组，不能越出视口 |
| 类型选择、筛选排序、导出配置 | `ResponsiveDialog` 底部 sheet | 居中对话框 | 标题固定、内容滚动、确认区固定 |
| 新增/编辑、关联对象选择 | `ResponsiveDialog` 全屏 | 宽对话框 | 手机单列表单，桌面按字段分组双列 |
| 票据详情 | 全屏详情 | 右侧面板 | 支持返回、深链接与状态恢复 |
| 原票照片 | 现有 `PhotoLightbox` | 现有 `PhotoLightbox` | 保持照片浏览器交互 |
| 纪念票面预览 | sheet，内容自适应宽度 | 居中对话框 | 预览尺寸与导出尺寸分离 |
| 删除确认 | 统一确认组件 | 统一确认组件 | 取消默认可见，危险操作明确 |

沿用弹层栈、焦点管理和返回关闭规则，避免页面与通用弹窗重复注册造成一次返回关闭多个层。打开弹层锁定背景滚动，浏览器返回先关闭顶层；全屏长表单不允许下拉手势关闭。

已修改的表单通过返回、关闭、遮罩或手势退出时，需要统一的放弃更改提示；识别、保存过程中避免重复提交，保存失败保留输入。短 sheet 的下拉关闭只在头部手势区触发，不抢正文滚动。

### 7.3 输入与显示边界

编辑表单分为“核心信息、原票图片、补充信息、关联经历”。智能填充放在内容区明确入口，处理后进入字段核对，不自动保存；识别失败可继续手填。保留已有关联原票图片，不因编辑其他字段而丢失。

视口高度采用动态视口并考虑系统安全区；键盘弹出时当前字段和提交操作可滚动到达，不被固定页脚遮挡。详情全屏时底部主导航不覆盖内容，批量栏协调全局选择状态。

亮色/暗色与各主题均沿用全局变量；强调色使用 `primary-*`，动态图形通过 `injectTheme()` 读取并响应主题切换。`text-gray-*`、`bg-white` 配套 `dark:`，Element Plus 不逐实例覆盖内部颜色。票面固有颜色仅限纪念票面，不作为应用控件品牌色。

## 8. 多类型票据扩展契约

### 8.1 分类与专属摘要

| 分类 / 类型 | 核心标题 | 专属信息 | 适用能力 |
| --- | --- | --- | --- |
| 交通 / 火车票 `train` | 出发站 → 到达站 | 车次、出发时间、座位、乘车人 | 交通统计、原票、纪念票面 |
| 交通 / 机票 `flight` | 出发城市/机场 → 到达城市/机场 | 航班、起降时间、乘机人 | 交通统计、原票 |
| 游览 / 景区门票 `attraction` | 景区名称 | 游览日期/有效期、地址、票种 | 原票、地点/回忆关联 |
| 演出 / 演唱会票 `concert` | 演出名称 | 演出者、场馆、场次、座位 | 原票、地点/回忆关联 |
| 电影 / 电影票 `movie` | 电影名称 | 影院、影厅、场次、座位 | 原票、回忆关联 |

分类负责导航，类型负责表单与详情，不把“高铁/动车”升级为与电影票同层级的类别。

### 8.2 通用字段与身份

通用展示契约包含：稳定身份、类型、标题、发生时间/时间范围、时间精度、可选地点、可选金额与币种、原票图片引用、备注、关联摘要；专属字段由类型定义。

- 现有两个票据表可分阶段保留，通过适配器统一输出，首期不要求整体迁移成单表。
- 实体引用统一使用 `(type, id)`，卡片 key、选择状态、删除、导出、缓存和关联都使用组合身份，不假定不同票据表的 ID 永远不重复。
- 区分发生日期、上传日期、拍摄日期；只有日期的门票不补成虚构的精确时刻，未知日期归入“日期待补充”。
- 到达时间可能跨日；发生时间按现有项目时间策略存储和展示，地点和时区缺失时不推导不存在的准确时间。
- 缺失价格表示“未填写”，不是免费；没有交通信息时不显示 0 km、0 小时。
- 原票照片与实体关系独立，删除照片后票据保留并显示“原票图片已不可用”。

类型注册应声明摘要、详情、表单、可用筛选、排序、统计及导出能力。新增类型不能依赖 `trainCode/from/to` 填入影片名称或场馆；未知类型提供可读的基础摘要与类型提示，不误识别成机票。

### 8.3 兼容与导出

现有历史票据、OCR、JSON/CSV 导入导出和火车票纪念 PNG 保持可用。新格式包含版本和类型信息，兼容读取旧交通格式；CSV 使用通用列与明确的类型专属列，不能通过列名猜错类型。

导出面板明确“当前筛选 N 张”或“已选 N 张”。PNG 纪念票面只对支持的类型启用；混合选择时明确支持/跳过数量，再执行，不静默遗漏。其他类型的原图查看和下载能力不与纪念 PNG 混为一项。

回忆服务当前只接受 `train/flight`，未来开放新类型须同步扩展验证、序列化、关系引用和失效引用处理，不能只改前端类型枚举。

## 9. 状态、权限与一致性

| 状态 | 要求 |
| --- | --- |
| 无票据 | “还没有票据”，提供新增与导入入口 |
| 筛选无结果 | “没有符合条件的票据”，提供清空筛选，不使用首次收藏空态 |
| 主列表加载失败 | 独立重试，保留条件；有缓存时明确提示更新失败 |
| 关联区加载失败 | 保持核心票据可浏览，只重试关联区 |
| 图片不可用 | 占位与说明，不显示无限加载 |
| 保存/关联失败 | 保留草稿、选择与上下文，提供重试 |
| 对象已删除或权限变化 | 刷新关系，显示不可用提示，不跳转错误对象 |
| 部分批量失败 | 保留失败项与可重试操作，成功项不重复执行 |

服务端校验票据及关联对象的所有权/编辑权限；搜索和反向查询不得暴露其他用户对象。首期不扩展共享票据权限体系。

照片、票据、相册、回忆的删除行为需解耦：解除关联不删实体，删票据不删原图或关联经历，删相册/回忆清理其关系不删票据。历史无效引用需有兼容读取策略，避免把缺失火车票错误展示为机票。

新关联能力需要服务端支持查询、创建和解除关系，并与现有 `MemoryTicket` 保持单一事实来源；不能在前端另存一套互不一致的回忆关系。相册关系可新增持久存储，候选关系与确认关系分别表达。

## 12. 评审建议

建议整体采用“票夹 + 相册内入口 + 双向关联”的方向，首期同时覆盖现有火车票和机票。具体视觉稿可在本方案评审后产出，重点先确认列表、手机全屏详情、关联选择器和新增编辑四种界面。

后续需要评估而不阻塞本方案的事项：旅程是否具备长期稳定身份；新类型 OCR 的输入样本与识别范围；历史时间数据的时区一致性。若旅程尚无稳定身份，按本方案以候选入口完成首期，不增加平行旅程实体。
