# 人物多外观簇：简化设计

更新于 2026-11-06。实现已接入，验证范围记录于文末。
替代此前的多版本、事件流和独立人工约束表方案。

## 1. 最终范围

只新增一张 `face_clusters` 表，在 `faces` 增加一个 `face_cluster_id` 字段。继续使用现有 `face_identities`、任务表和 `SystemState`。

一个人物有多个簇，一个簇有多张脸，一张脸最多属于一个簇。用户合并人物时修改簇归属，后台另有严格物理合簇步骤。用户仍只做添加、移出、合并。

不建设独立纠错表、事件总线、聚类版本表、多版本成员表、负例学习和复杂参考晋升系统。新版本直接使用当前簇结果，不同时维护多个在线版本。

## 2. 数据库

### 2.1 新表 face_clusters

| 字段 | 类型/含义 |
|---|---|
| id | UUID 主键 |
| owner_id | 用户外键，非空 |
| identity_id | 人物外键，可空；为空表示尚未归属人物的候选簇 |
| center | VECTOR(512)，成员单位向量均值再次归一化，用于检索 |
| vector_sum | VECTOR(512)，成员单位向量的和，用于增删后更新中心 |
| anchor_face_id | faces 外键，可空；固定核心样本，防止簇中心不断漂移 |
| face_count | 有效成员数量 |
| status | pending / active；仅供后台调度，UI 不展示 |
| revision | 整数版本，中心或归属变化时递增 |
| created_at / updated_at | 时间 |

PG 使用现有 VECTOR 包装对应 vector(512)，SQLite 对应 JSON 数组。复用原始脸向量，不再存一张成员关系表。中心无效、零向量或空簇不参加检索。

`vector_sum` 是加速统计，不是另一个识别特征。计算中采用足够精度，定期或发现偏差时从成员重算；事务重试不能重复加减。删除最后一个成员时删除空簇，不生成零中心。

索引：

- `(owner_id, identity_id, id)`：人物所属簇。
- `(owner_id, status, id)`：用户候选簇。
- 簇候选使用任务内近邻索引。
- SQLite 不创建数据库向量索引，使用进程内矩阵/近邻索引。

### 2.2 faces 只增加一个字段

| 字段 | 含义 |
|---|---|
| face_cluster_id | 可空外键，指向 face_clusters |

增加 `(face_cluster_id, photo_id)` 索引，支持簇成员读取及不同照片数量统计。另加未分簇有效人脸的 `(id, photo_id)` 部分索引，供有界游标扫描。SQLite 显式选择该索引，并以照片主键 EXISTS 验证用户与删除状态。

保留 `face_identity_id` 和现有覆盖索引，作为列表、时间线和同框相册的快速查询字段。已有业务不必为每次读取新增联表。

必须保持：有簇的脸，其 face_identity_id 与簇 identity_id 相同；无簇的脸默认人物为空，只有升级尚未处理的旧记录允许临时例外。成员变化、簇统计与人物查询字段同事务更新。

不增加人工约束标记，不保存排除记忆。移出只改变当前归属；该脸以后参与自动聚类或重扫时，可能再次匹配到原人物。

### 2.3 状态不新增表

复用 SystemState，按用户保存一个 `face_cluster_state:<owner_id>`：

- phase：initializing / ready / resetting / failed。
- generation、checkpoint：任务恢复、过期 worker 隔离。
- revision：簇索引失效信号。
- params、request_id、cleared、error 用于保存重置参数、请求幂等、清理阶段和可重试错误。

它只是现有表内的一条状态，不保存每次操作历史，不保留多代聚类数据。checkpoint 与对应数据修改同事务提交。

## 3. 聚类方式

### 3.1 第一版采用增量紧凑簇

统一使用余弦距离，越小越严格。取消原来的 DBSCAN 后 `threshold + 0.08` 宽松合并。第一版也不再对整个未归属池反复执行密集 DBSCAN。

从旧向量或新脸建立簇时：

1. 批量查询最近的若干簇中心。
2. 检查该脸与中心、核心 anchor 的距离都满足入簇阈值。
3. 检查候选是否存在明显身份竞争；分不清则不强行加入已有命名人物。
4. 可以加入则更新成员、向量和与中心；不能加入则建立小候选簇，或等待下一批处理。
5. 小簇不断积累，达到配置的不同照片数量后可创建未命名人物。人工添加、迁移的旧人物不受这个门槛限制。

建簇不是把相似关系做传递闭包。A 接近 B、B 接近 C，不自动意味着 C 可以入 A 的簇。anchor 在普通增量加入时保持不变；只有 anchor 删除/移出时，才从剩余成员选接近现有中心的有效样本替换并校验簇。

中心可以由所有有效成员平均得到，但只在相对紧凑的外观簇内计算，绝不把某个人物的全部簇合成大平均。

按 face ID 顺序处理，每批最多 512 张脸。同批的新候选簇立即参与后续匹配，已提交簇的中心在批次结束更新。结果仍可能受数据及顺序影响，真实相册需要测量拆分和误合并情况。

### 3.2 簇如何归属人物

归属判断和物理合簇分开：

- 新稳定簇与已有簇中心接近，仅成为归属候选。
- 从每个簇流式选择最接近中心、来自不同照片的最多 3 张脸作双向核验，每侧至少两张。代表样本在当前步骤内缓存。
- 选择满足绝对距离要求的最近人物簇，再进行实际成员核验。簇级归属不要求领先第二个人物 0.05。
- 通过检查只设置新簇 identity_id；不把两个簇的成员平均到一起。
- 不能确定、且自身已达到显示门槛的簇创建新未命名人物；不足门槛继续作为候选。

已命名人物的身份由用户管理。已有的两个未命名人物可以经过额外的严格中心距离和代表样本核验自动归并，各外观簇分别保留。

有限成员核验直接从 faces 按 cluster 索引取样/缓存，不另建参考样本表，也不要求用户挑照片。

### 3.3 参数

普通档为新的默认配置，聚类距离 0.5、物理合簇距离 0.25、人物归属距离 0.425、未命名人物合并中心距离 0.2，最低不同照片数为 5。各阈值可以独立自定义。旧设置未保存新增阈值时，按其原聚类距离的 0.5、0.85、0.4 倍分别补全。

ANN 初始候选上限为 64。单脸直接入簇时执行 0.05 的竞争差距判断，暂未入簇的脸可以在后续簇级整理中经严格距离与成员检查归属。

入簇和簇归属比较对象不同，不能用一个阈值兼任所有判断，也不能只靠数值大小说明严格程度。取消 +0.08 后，通过带标注的兄弟姐妹、侧脸和跨年照片标定具体值。

调整参数默认影响后续处理；不偷偷改变全部已有结果。需要统一应用新参数时，用户选择“重置人物聚类”。

### 3.4 严格物理合簇

每轮聚类收尾、候选簇最终晋升人物之前，对紧凑簇进行物理整理。未归属的单脸簇也可参与，合并后再按不同照片数量判断是否显示人物。

- 同一人物内部可以合并，未归属簇之间也可以合并。未归属簇可按严格距离和全部成员检查并入已有的人物簇，簇级物理合并取消人物竞争差距判断。
- 两个簇已属于不同人物时，保持各自身份。
- 中心之间、核心之间，以及双向中心到核心的余弦距离均须小于物理合簇距离。普通档为 0.25，运行时也受普通入簇阈值上限约束。
- 候选通过后，按成员索引流式检查所有有效成员。每张脸到合并后中心和双方原核心的距离都须小于普通入簇阈值，统计数量也须一致。
- 未归属簇归入已有人物时保留已有人物的目标簇。其余情况小簇迁入大簇，相同大小以 UUID 固定顺序决定方向。更新成员外键、人物归属、向量和、均值及数量，保留目标核心，最后删除源簇。
- 所有修改在用户锁保护的同一事务内提交。异常回滚会同时恢复成员、簇与统计，后续任务可以重试。

候选索引随合并更新中心，已删除簇从候选中排除，完成后重新加载有效索引再执行人物归属。大量相同候选占据近邻结果时，剩余碎片可在后续轮次继续整理。

旧配置缺少新增字段时，分别以 0.5 和 0.85 补全物理合簇与人物归属距离。预设及自定义配置保存独立阈值。

### 3.5 识别档位和未命名人物整理

设置提供宽松、普通、严格和自定义。选择预设填入整组参数，手动修改具体参数会显示自定义。保存聚类相关参数后，通过现有持久化任务后台整理已有的未命名人物。

| 参数 | 宽松 | 普通默认 | 严格 |
|---|---|---|---|
| 人脸检测置信度 | 0.65 | 0.7 | 0.8 |
| 单脸入簇距离 | 0.6 | 0.5 | 0.35 |
| 物理合簇距离 | 0.3 | 0.25 | 0.175 |
| 人物归属与样本距离 | 0.51 | 0.425 | 0.2975 |
| 未命名人物合并中心距离 | 0.24 | 0.2 | 0.14 |
| 人物最低不同照片数 | 3 | 5 | 8 |
| 重扫高置信度距离 | 0.4 | 0.35 | 0.28 |
| 重扫候选距离 | 0.55 | 0.45 | 0.38 |
| 重扫移出距离 | 0.65 | 0.52 | 0.48 |

后台在新簇晋升之后，对名称恰为“未命名”的有效人物做归并。候选簇中心必须低于未命名人物合并阈值，双方代表样本也须通过人物归属阈值的双向匹配。通过后复用人物合并逻辑，在同一事务更新所有簇和人脸归属、时间线引用及源人物软删除，保留目标人物封面和各簇中心。

代表样本从所有有效成员中选取最接近中心的三张不同照片，流式处理时只保留三个候选。该规则改善按人脸 ID 取前几张时容易受到早期低质量照片影响的问题。

## 4. 新照片流程

`现有模型提取向量 → 批量匹配簇 → 更新簇或产生候选簇 → 继承/确定人物归属`

AI 推理照旧。聚类仍在现有 CPU 任务中运行，新脸先落库，调度器合并同用户的聚类任务。增量匹配计算在写事务之外，结果批量提交。收尾物理合簇的成员复核与修改在同一用户锁事务中执行。

例如哥哥、弟弟各有若干外观簇：新脸分别得到两个孩子各自最佳的簇匹配结果。若二者接近就不强行归入任一已有人物。侧脸可以形成新簇，后续自动归属或被用户合并到已有的人物。

不能匹配的历史脸不在每批导入时全部重算：只处理新脸、候选簇及有限相似邻域。稀疏候选不足可以留到后续批次，不建立无限密集距离矩阵。

## 5. 用户操作

| 操作 | 数据修改 |
|---|---|
| 添加一张脸到人物 A | 从旧簇移出；加入 A 中兼容的簇，没有则建一个属于 A 的新簇 |
| 从人物 A 移出一张脸 | 从簇移出并更新中心；清空两个归属字段，不记录排除约束 |
| 合并人物 A 到 B | 更新 A 所有簇的 identity_id；集合式更新相关 faces.face_identity_id；沿用现有逻辑处理封面、时间线关系及源人物软删除；不改簇中心 |
| 删除照片/人脸 | 扣减簇统计，更新中心；删除空簇，修复 anchor 和封面 |
| 恢复照片/人脸 | 验证原簇仍有效再恢复归属；不存在则重新入候选，不能复活被重置的旧人物 |

移出不会把同簇其他脸一起搬走，也不会自动把相像的新脸永久排除。该简化版明确放弃负例学习；新照片的改进来自更紧凑的簇和人物竞争判断。

现有批量添加、相似脸添加、撤销、重扫等路径全部使用同一个归属服务，不能有接口只更新 face_identity_id。撤销需要恢复两个归属字段和受影响簇统计。

## 6. 无感升级

### 6.1 结构迁移

同一 PR 提交 PG 和 SQLite 各一个 Alembic 迁移，从实际 head 生成。

1. 创建 face_clusters 及其索引。
2. faces 只增加可空 face_cluster_id。
3. 创建簇成员查询索引。
4. 不删原字段、不改原人物归属、不在 Alembic 中聚类或调用 AI。
5. 在同一迁移事务中，为有有效旧人脸的用户一次性安排初始化任务。已有 pending 聚类任务复用并保留参数，设置 auto=false 以绕过导入节流。processing 任务保留，另建 pending 后续任务。

PG 正常增加可空列和外键约束。SQLite 使用可空、默认 NULL 的 REFERENCES 列追加方式，避免为了添加外键强制重建 faces；实际生成 SQL 必须检查。新簇表先建，随后 faces 追加引用列，允许 anchor 与 face_cluster_id 形成合法引用关系；删除由集中服务先清引用再删，避免循环级联。

新增 `(face_cluster_id, photo_id)` 索引仍有一次建索引成本，不能声称升级完全零停顿；用旧库副本测量升级窗口。保留现有数据库备份机制，SQLite 使用一致备份而不是裸复制活动 db 文件。

### 6.2 后台建立簇

迁移提交后，既有任务 worker 消费已持久化的初始化任务。进程重启通过任务恢复机制续跑，应用启动不再扫描照片、人脸或用户来安排初始化。重复执行 upgrade head 由 Alembic 版本表保证跳过已执行迁移。

- 旧人物和归属照常显示，原姓名、ID、描述、标签、封面、隐藏状态全部保留。
- 按旧人物分别处理其已有脸，只在人物内部生成多个紧凑簇，不跨旧人物自动归并。
- 已有归属但无法形成稳定组的脸建立小簇，仍归属原人物；不因最低照片数被隐藏或丢掉。
- 原来没有人物的脸按新算法处理；原始向量直接复用，不重跑模型。
- 已经混合了两个孩子的旧人物不会在升级时擅自改名/拆成两个人物。新结构能保留内部子簇，但历史身份错误仍需正常添加/移出或用户主动重置。

任务短批处理、检查点恢复；失败不清空旧人物。初始化期间自动匹配等待初始化完成，检测、上传、浏览及人工编辑正常继续。

不建立事件流：每个计算批次写入前重新读取该批人脸当前归属。只有旧人物未变化且尚未分簇的记录才提交；变化的记录跳过重试。人工操作与自动写入通过同一用户状态行的短事务门禁串行提交，计算阶段不持锁。

PostgreSQL 使用由用户 UUID 派生的事务 advisory lock，SQLite 通过 SystemState 的 INSERT ON CONFLICT 和事务内 UPDATE 取得写锁。提交时检查 generation、revision 和 phase，人工编辑触发索引重载和游标回查。

初始化收尾查询仍有旧人物但无簇的记录，处理完后才标记 ready；不能只靠最大 face ID 判断完成，避免漏掉并发提交或旧记录修改。新脸的无归属记录交给正常增量任务。

### 6.3 回退

未完成初始化时停止后台任务即可保留原展示。已完成后，faces.face_identity_id 仍兼容旧读取。

应用降级必须先停止新 worker，保证没有重置进行到一半。schema downgrade 的具体顺序需验证 SQLite 外键和列删除限制；必要时使用受控表复制，不能宣称 downgrade 也零成本。恢复重置之前的数据依赖备份，不由 schema downgrade 自动恢复。

旧数据没有模型版本信息，不能凭当前配置断言其来源。此改动不新增模型切换机制：保持现有模型与向量兼容约定，不自动重新提取向量；已知模型不兼容时不得混算。完整模型空间迁移作为单独需求，不能用本次聚类重置替代。

## 7. 全部打散重置

设置只新增一个“重置人物聚类”按钮和进度显示。确认文案明确：保留原图与检测结果；清除人物归属、姓名、合并结果、封面等人物整理结果，重新生成未命名人物。

不做后台双版本切换或重置结果快照，复用现有任务实现可恢复的分步流程：

1. 接收请求，写 resetting 状态、递增 generation、固定本次参数；重复请求返回同一正在执行的任务。
2. 所有旧任务提交时发现 generation 变化即放弃，不能写回旧结果。
3. 人物相关读取统一显示“正在重新整理”，人物编辑暂不可用；普通照片浏览、上传与人脸检测照常。
4. 在一次清理事务中清空本用户 faces 的 face_cluster_id、face_identity_id、recognize_confidence，包含软删除记录。
5. 清空本用户簇，旧人物软删除并清封面引用。引用旧人物的时间线设置清除。条件相册保留原规则，旧人物条件暂时没有匹配结果，用户可以重新选择人物。
6. 使用已有有效向量按新参数重新聚类，创建未命名人物。新上传的人脸由同一个代次的任务接续处理。
7. 完成检查点范围并校验后设 ready，刷新相关缓存和条件相册；水位之后的新脸继续增量处理，不等待持续上传永远结束。

清理阶段和每批重建分别提交状态，进程重启后扫描尚未分簇的脸继续处理。重置期间 faces 路由统一返回整理中，编辑暂不可用。清理事务撤下旧人物，重建期间保留空人物归属，最后一个事务统一发布新人物。完成后刷新条件相册。

失败保持“整理失败，可重试”，旧数据不会自动恢复。此简化版本不提供重置撤销；确认文案必须说明。仅实际用户点击重置才执行破坏性清理，正常升级绝不触发。

## 8. 两种数据库的性能

### 8.1 不改变现有展示查询

人物列表、人物照片、同框和时间线保留原 faces.face_identity_id 查询与覆盖索引。只在请求级检查一次用户状态，不能每行检查，不读取向量。

加入、移出一个簇只增减 vector_sum、更新 center/count；常规操作不重读整个簇。distinct photo 数按簇索引在批次结束统计，避免每张脸执行 COUNT DISTINCT。合并人物使用集合式 UPDATE，替代全量 ORM 逐条循环。

### 8.2 共同的候选索引

两个数据库都按用户流式读取簇中心与核心样本，建立任务内 float32 矩阵。最多 8192 个簇时批量矩阵计算候选，超过后使用 hnswlib 核心向量索引召回。近邻索引从 256 个簇开始维护，也用于单簇归属候选。随后精确比较中心、核心样本和不同人物的距离差。向量进入连续数组后释放 Python 浮点列表，索引在当前任务批次间复用。

每批计算前读取 generation/revision。计算在写事务之外，提交前重新加用户级事务锁并核对版本。人工变更发生后重建索引。手动添加只加载目标人物的簇。

### 8.3 数据库访问

PostgreSQL 的原始人脸向量索引继续服务于相似脸和重扫。批量聚类使用按用户隔离的进程内候选索引，候选簇和人脸按主键集合复核。簇表与人脸表的 B-tree 索引服务于成员和归属查询。

SQLite 的未分簇游标使用 `INDEXED BY ix_faces_unclustered`。候选验证从有界人脸 ID 开始，以照片主键 EXISTS 校验用户，避免遍历用户所有照片并排序宽向量记录。每批最多 512 张脸。新簇、成员归属集合式写入，减少宽人脸记录的重复改写。

核心向量固定，中心变化仅更新精排矩阵。任务内索引从数据库重建，进程重启通过现有任务与 SystemState 检查点恢复。原生依赖已经在 Windows 开发环境构建，容器构建阶段补充 C++ 编译器，桌面 spec 显式包含 hnswlib。

### 8.4 验收门禁

本地性能测试对照固定旧版代码 SHA，双库分别测量 1k、5k、10k 人脸完整聚类耗时。数据为每个外观十张照片的合成向量，计时前为两个实现分别创建新数据库索引。

后续真实相册发布验收还需覆盖以下项目。

- 常用展示查询 P95 不劣于旧版。
- 新照片匹配 P95、整批导入吞吐不劣于旧版。
- 全量初始化/重建耗时与内存预算达标，不能只给热缓存成绩。
- SQLite 写锁等待不恶化，无长事务内向量计算。
- 兄弟姐妹误合并改善，侧脸和跨年找回率、未归属比例同时通过标注数据验收，不能靠全部拒绝匹配换速度。

本次 SQLite 使用 EXPLAIN QUERY PLAN 确认未分簇部分索引与照片主键查询。50k/100k、C 接近 N、冷/热缓存多轮 P95 和真实儿童标注照片的准确率尚需专门验证。新增索引和统计字段有存储成本。
