# 行程照片自动关联

行程匹配由 `app/service/journey.py` 负责，复用现有记忆、照片、地点、票据及证据表。结果为待确认的记忆，不自动确认用户经历。

## 触发职责

- 火车票创建、识别保存、修改和票夹导入：在保存事务内通过 `journey_queue.enqueue` 写入 `ASSOCIATE_JOURNEYS` 任务。
- 照片批量入库、元数据提取/重建、人工位置修改、拍摄时间修改：同样提交关联任务，因此支持先票后照片和先照片后票。
- 记忆页的“发现”：调用同一个服务补算历史票据，并继续原有照片记忆发现。
- 现有 worker 执行关联，watchdog 可唤醒持久化任务。识别和扫描不直接等待关联计算，不要求整库扫描结束；元数据随后补全会再触发。

同一用户只保留一个 pending 任务。已有任务 processing 时，后续数据变更仍留一个 pending 任务，避免执行时发生的新导入被漏掉。任务与源数据共同提交或回滚，不在票据保存事务中访问 railway。

## 匹配规则

1. 首版仅火车票。使用已有完整 `date_time`；缺失或占位年份不匹配。新识别票据缺少年份或识别结果声明年份为推测时，在原票照片的 `processed_tasks.ticket_time_sources` 中记录来源，保存票据但不自动关联；用户明确修改乘车时间后解除限制。原票图片拍摄时间不替代行程关联时间。旧数据没有来源记录，无法追溯历史识别是否推测过年份，按已保存的完整日期时间处理。
2. 按出发、到达站名查 railway.station 的省份和城市；允许站名末尾的“站”差异。缺省市或同名车站对应多个省市时跳过，不猜测。
3. 出发前 24 小时至出发时刻，匹配出发城市。后窗口为出发时刻后 48 小时；正的 `total_running_time` 存在时，窗口改为推算到达时刻起 48 小时，证据标记为估算。
4. 城市允许“杭州/杭州市”等差异，同时要求省份一致。无位置、非本人、已删除、截图和本人的车票原图均排除。一侧有照片即可生成候选，两侧都有证据时置信度更高。
5. 每张车票使用稳定指纹生成一个候选；新照片或票据修改后刷新未编辑的候选。确认、忽略、删除、合并、拆分、编辑、移除照片或票据等人工操作不会被自动覆盖。未编辑候选不再有匹配照片或车票删除时，候选退为 superseded，不删除照片。

`POST /memories/discover` 对应的记忆发现请求增加 `journey_before_hours` 和 `journey_after_hours`（1–168 小时，默认 24/48）。自动任务使用默认窗口。无 railway 配置或数据库故障时，后台任务使用既有失败重试机制；手动发现仍允许生成普通照片记忆。

本次只增加 Python 的 TaskType 值，数据库 `tasks.type` 本来为 String(50)，没有 ORM 表结构变动，无需数据库迁移。运行实例须已迁移到支持 memories 等既有表的版本。

首版不合并多张车票为整段旅行，不跨城市猜测无位置照片，也不自动生成故事。
