# 铁路历史数据同步与查询（REQ-196）

现有数据仓库 https://github.com/LC044/trailsnap-railway-history 的基础方向可用，但原实现不能满足完整需求。远端采集 workflow 与本地检查结果一致。实现修改分为独立数据仓库与 TrailSnap 两部分，当前保留为本地工作区改动，尚未提交、推送或执行远端发布。

| 原问题 | 修改方案与实现 |
| --- | --- |
| 列表重试只修复 HTTP 状态，没有把返回数据加入枚举 | 调用方直接重试并使用成功结果，200 条截断递归分拆，按内部号和公开车次去重 |
| 八类前缀漏掉纯数字普客，TEST_PREFIX 只取首字母 | 增加数字、L/A 类入口，测试前缀按完整输入使用；未认识的新类型不宣称已覆盖 |
| 用采集日作为运行版本日，A→B→A 或间歇运行无法表达 | 以查询的运行日期记录 dates，原 fd/ld 仅代表观测边界，绝不将边界内全部日期当作已验证 |
| 只保留历史名称，其他站点字段覆盖丢失 | 保存版本化原始字段 raw_fields、GPS 原始对象及来源、坐标系说明，另记状态变化；新字段不需要加本地 ORM 列 |
| 失败、测试采集被当作全量，缺少项误报停运 | 失败列表阻止发布本轮，详情失败保留成功记录及列表起终站；测试必须隔离目录，CI 不提交或发布测试；不由缺少车次推断停运 |
| 读取损坏历史时静默当成空库、覆盖历史 | 缺文件才初始化；JSON 或 JSONL 损坏立即失败，发布时检测实体被删除 |
| Release 固定 data-auto、失败也发布、缺少客户端协议 | 每次运行独立 Release，仅成功正式采集发布；不可变 SHA-256 gzip 包、单调 sequence、全历史 snapshot、增量 deltas，先提交所有包再发布 |
| 本地固定 CSV、单内部号唯一约束不能承载历史 | 新增可重建的 railway-history.sqlite 参考缓存；保留原种子数据库及 ID，异步更新站名/别名/城市查询投影，无 ORM 结构修改 |

## 数据协议

数据仓库的 `data/feed/manifest.json` 包含 `schema_version=1`、单调 `sequence`、采集覆盖说明 `metadata`、完整历史 `snapshot`、全部不可变增量描述 `deltas`。每个描述包含相对路径、压缩字节数、SHA-256。包是 gzip JSON，包含序号、是否完整快照和实体 upserts。站点实体含所有站名、原始字段版本和状态事件；车次实体含所有内容版本及其实际采样日。

首次同步下载一个包含保留历史的 snapshot，后续只下载游标后的 delta。中间游标缺失可用 snapshot 恢复。每个包在一个 SQLite 事务里落库并推进游标；校验失败或写入中断不会推进当前包，已完成的前序包可继续恢复。重复同步不重新下载包；多个服务进程在 SQLite 写事务中重新检查游标。未知协议主版本拒绝同步，保留已有离线缓存。

SHA-256 用于传输完整性，不替代 GitHub 账号和 HTTPS 的信任。Git 仓库中保留所有历史包；GitHub Artifact 只有短期诊断用途，不能作为历史的唯一来源。Release 附件含全历史压缩包和 manifest，自动客户端使用 GitHub raw 上的 feed。snapshot 文件名包含内容哈希，因此远端清单和包可独立缓存。

当前 v1 增量粒度是变化实体：一条车次有新采样日时会重发该车次的历史记录。不是逐站停靠行的最小增量；历史增长后可在协议 v2 引入按观测事件分片和清单分段。不能删除旧 v1 包来节省空间，否则老客户端无法继续增量同步。

## 查询规则

- `GET /api/railway/history/status`：本地游标和覆盖信息。
- `GET /api/railway/history/stations?name_or_code=旧站名`：按电报码或任意历史名称查询，包含不再出现在新车站表中的站点。歧义返回多个候选，不静默改写票面名称。
- `GET /api/railway/history/trains?train_code=C20&query_date=2026-10-23`：按车次和日期查询，可以传 `departure_station`、`arrival_station` 截取票面区间。
- 优先完整时刻表的精确观测日；没有当天完整时刻表时，匹配最近的完整观测日。无完整时刻表的车次使用列表起终站；未知车次只使用票面起终站。日期距离相同优先较新的日期；同日多个版本用起终站消歧。
- 返回 `match=exact/nearest/endpoints`、`matched_date` 和原始版本指纹，最近匹配不代表已证实当天运行。仅列表存在时，时长和停靠站为空；起终站坐标足够时仍可估算端点距离。
- 里程为相邻停靠站 Haversine 距离之和 × 1.2，单位 km，保留 1 位小数；未知车次使用端点直线距离 × 1.2。`distance_source=gps-haversine-x1.2` 明确标注估算；不是铁路实际计费里程。
- 坐标缺失、非法或中间任何一段不可算，则区间里程为 null。不会将未知距离当 0，也不会累加部分站段冒充完整里程。站点坐标随字段版本保存，查询按匹配日期选最近观测坐标。
- 时长使用原始 running_time 或到发钟点与跨日信息，区间起点扣除停站时长，处理 23:55 到达、00:05 发车的跨日停站。

票据识别补全与批量里程统计已接入历史缓存；编辑器查询携带乘车日期，显示最近记录提示，切换日期/车次清空旧候选。首次同步前保留静态种子查询。原有部分管理型时刻表 CRUD 仍操作旧种子表，不作为历史查询接口。

## 部署与本地验收

在独立数据仓库合入本地修改后，`npm ci`、`npm test`、`npm run dev`。GitHub Action 每天北京时间 03:00 运行，最长 330 分钟，串行发布避免数据竞态，公开仓库需要开启工作流 contents 写权限。首次正式采集前确认保留当前 `data/`：它有用户原有的删除改动和正在运行的旧采集进程，本轮没有覆盖它们。采集任务支持同查询日的详情 checkpoint；超时/失败时保留 snapshot artifact 便于人工续跑。

TrailSnap 服务启动 60 秒后通过现有 JobScheduler 同步一次，以后默认每天同步。环境变量：

- `RAILWAY_HISTORY_SYNC_ENABLED=0`：禁用自动同步。
- `RAILWAY_HISTORY_SYNC_SECONDS=86400`：间隔秒数，最低 3600。
- `RAILWAY_HISTORY_FEED_URL`：HTTPS feed 目录，默认 raw.githubusercontent.com/LC044/trailsnap-railway-history/main/data/feed/。
- `RAILWAY_HISTORY_DB`：缓存文件路径，默认 DATA_DIR/railway-history.sqlite，随图库数据目录备份迁移。

网络不通或远端尚未发布新协议时，后台记录错误并继续使用现有本地数据；不阻塞鉴权和服务启动。车站投影会在成功同步后幂等更新，旧别名及省区等本地附加资料保留。

首批可复现导入（从 `package/server` 执行，不操作用户图库）：

```powershell
.venv/Scripts/python.exe -m railway.history_cli --db ../../tmp/cr-12306-train-info/snapshot/initial-v1/railway-history.sqlite --feed-dir ../../tmp/cr-12306-train-info/snapshot/initial-v1/data/feed --train C20 --date 2026-10-23
```

采集器环境变量 DATA_DIR、SNAPSHOT_DIR 用于隔离数据；TEST_PREFIX、TEST_LIMIT 只用于样本验证。重放已有快照时指定 REPLAY_SNAPSHOT_DIR、REPLAY_DATE，缺少列表映射的详情必须显式给出 REPLAY_QUERY_DATE，避免把旧样本误标成今天。

## 本地车站坐标同步与缺失补齐

铁路 `station` 表新增可空 `latitude`、`longitude`、`coordinate_source`、`coordinate_system`、`coordinates_updated_at`，以及补齐状态、最后查询时间和下次重试时间。普通车站查询返回经纬度、来源、参考系和更新时间。同步历史包时投影最新有效 GPS，保留车站 ID 和本地资料；有效本地/天地图坐标不会被覆盖。源坐标变化可更新既有 `12306` 坐标，历史包中的过去坐标仍保留。投影模式版本升级会补做一次已有 feed 的坐标入库，无需等待 GitHub 产生新序号。

铁路库与照片主库独立，启动时执行独立 Alembic 链：PostgreSQL 位于 `alembic/railway_versions/`，SQLite 位于 `alembic_sqlite/railway_versions/`，版本表为 `alembic_version_railway`。不修改主库迁移头；新库和旧库均支持幂等升级，原有站点 ID 不变。桌面构建包含迁移运行文件。

缺失坐标独立于 feed 更新任务，启动后 120 秒检查，此后每小时执行。默认每批最多 50 站、45 秒预算，请求间隔 250 毫秒；`RAILWAY_COORDINATE_BATCH_SIZE` 可调整批量，`RAILWAY_COORDINATE_SYNC_ENABLED=0` 可关闭补齐。优先使用服务端环境变量 `RAILWAY_TIANDITU_KEY`，否则复用已启用管理员的天地图地图配置。无可用 Key 时跳过，不影响历史数据同步。

调用天地图官方 POI 查询接口，仅接受站名规范化后精确匹配、城市一致且有效的唯一坐标；不接收行政区中心、站内店铺或含糊的多个结果。结果标记 `tianditu` / `CGCS2000`；种子坐标未确认参考系时标记 `unknown`。未找到/歧义结果七天后重试，限额、鉴权或网络错误一天后重试；限额和 Key 错误停止当前批次。凭据不写入车站数据库、feed、日志或 GitHub。

成功坐标同时写入本地历史查询的坐标补充表。按历史日期计算距离时优先使用当时历史包坐标，缺失才用本地补齐值；保留 GPS 直线距离乘 1.2 的估算标识，不作为实际铁路营业里程。停用、已拆除或地图无法可靠定位的历史车站允许继续为空。
