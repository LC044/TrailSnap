## Agent Conversation System Design

### Feature Description

The current chat history is stored in memory and does not support multiple sessions. When the user closes or restarts the application, the chat history is lost. To prevent chat history loss, the conversation records need to be stored in a local database.

### Database Design

The table descriptions below are for reference only. You can modify or add new fields as needed, or reserve fields for future feature expansion.

1. **Sessions table (`agent_sessions`)**
   1. `id`: Session ID, primary key (UUID)
   2. `user_id`: User ID, foreign key referencing the `user_id` in the users table
   3. `created_at`: Creation time, records when the session was created
   4. `title`: Session title, user can customize the session title
   5. `status`: Session status, records whether the session has ended
   6. `context_summary`: Session context summary, records the context summary of the session
   7. `summary_update_time`: Context summary update time, records when the context summary was last updated

2. **Messages table (`agent_messages`)**
   1. `id`: Message ID, primary key (auto-increment)
   2. `session_id`: Session ID, foreign key referencing the `id` in the sessions table
   3. `role`: Message role — `user` / `assistant` / `system`
   4. `content`: Message content, records the user's message or the agent's reply
   5. `content_type`: Message content type, e.g., text, image, audio
   6. `content_ext`: Message content extension, e.g., image URL, audio URL
   7. `token_count`: Message token count, for billing purposes
   8. `created_at`: Creation time, records when the message was sent

### Feature Extensions

3. Add backend API endpoints for getting the session list, switching sessions, creating sessions, deleting sessions, pinning sessions, deleting messages, etc.

## Token Management Feature

### Feature Description

Users can use tokens to call the corresponding user's API endpoints, such as querying the photo list, uploading photos, etc.

### Token Table (`agent_tokens`)

1. `id`: Token ID, primary key (UUID)
2. `user_id`: User ID, foreign key referencing the `user_id` in the users table
3. `name`: Token name, user-defined
4. `token`: Token value, randomly generated string for verifying user permissions
5. `created_at`: Creation time
6. `expires_at`: Expiration time
7. `is_deleted`: Whether deleted, default `False`

### Frontend

1. Add a token management page at `package/website/src/views/settings/Tokens.vue`. Users can view all tokens, create new tokens, and delete tokens.
2. When creating a new token, the user must enter a token name, select an expiration time, and verify their password.
3. When viewing tokens, the token name and token value are displayed. The user cannot directly view the full token value; they can only copy it. A tag indicates whether the token is expired.

When a token is deleted, it becomes invalid and can no longer be used to call API endpoints.

## Footprint Timeline Feature

### I. Overall Feature Definition

#### 1. Feature Name

Album Footprint Timeline

#### 2. Feature Positioning

Automatically generate a visual time + geographic trajectory based on photos' **capture time + province/city/district/scenic spot/detailed address** multi-level geographic location. Support multi-view browsing, filtering, and editing to satisfy users' need to view their life/travel footprints through photos.

#### 3. Target Devices

PC (web/client) and mobile (phone/tablet). Both platforms have identical functionality with adaptive layouts.

---

### II. Basic Display Rules

#### 1. Sorting Rules

1. All photos are displayed in **reverse chronological order** (newest first).
2. Photos taken at the same time and location are automatically aggregated into a group.
3. Photos without geographic location data are excluded from the timeline display.

#### 2. Geographic Location Display Priority (Fixed Rules)

The feature displays location names according to the following priority, **automatically matched and not changeable**:

1. First priority: **Scenic spot** (when scenic spot info is available, display: city + scenic spot)
2. Second priority: **District/County** (when no scenic spot but district is available, display: city + district)
3. Third priority: **City** (when no scenic spot/district, display city only)
4. Fourth priority: **Province/Country** (when no city, display province/country)

#### 3. Grouping and Aggregation Rules

1. **Group by day**: Photos taken on the same day are merged into one time node by default.
2. **Group by location**: Photos taken on the same day at the same location (scenic spot/district/city) are merged into one footprint point.
3. **Continuous trip aggregation**: When photos are taken in the same city for 3 or more consecutive days, they are automatically aggregated into "XX City · N-Day Trip", which can be expanded to view daily details.

---

### III. Multi-View Display (Both Platforms)

Two independent views are provided. Users can freely switch between them, and the view data is fully synchronized.

#### View 1: Standard Footprint Timeline (Default View)

1. Vertical timeline layout. The left side displays **time + geographic location**, the right side displays the corresponding photo cover thumbnails. Clicking opens all photos in that group.
2. Single footprint display format:
   - With scenic spot: `2026-03-25 · Hangzhou City · West Lake Scenic Area`
   - With district: `2026-03-24 · Beijing City · Chaoyang District`
   - City only: `2026-03-23 · Shanghai City`
3. Collapse/Expand: Support collapsing historical months/years for quick view compression.

#### View 2: Map Trajectory View

1. Left: Timeline thumbnail list; Right: Map panel.
2. The map automatically marks all photo shooting locations and **connects them with lines to generate a travel trajectory**.
3. Map marker rules:
   - Marker size: the more photos at a location, the larger the marker.
   - Clicking a marker: automatically displays all photos + time + address for that location.
4. Support trajectory show/hide and map fullscreen view.

---

### IV. Dual-Platform Display Adaptation

#### 1. Mobile (Phone/Tablet)

- Standard timeline: Single-column photos, vertical scrolling, location info pinned to top.
- Map view: Fullscreen map, photo list pops up from the bottom.
- Immersive view: Portrait fullscreen, floating info bar at the bottom.

#### 2. PC

- Standard timeline: Multi-column photo grid, time + location fixed on the left.
- Map view: Left-right split, map and timeline displayed on the same screen.

---

### Feature Optimization

1. Photos should be placed on the far right; time and location should be vertically centered relative to the photos.
2. The timeline does not necessarily group by month. If multiple months are in the same city, all photos from that city are placed in one time node.
3. A trip does not necessarily consist of consecutive dates. Even if a particular day has no photos, but the next photos are still in the same location, they are grouped together. The key criterion is whether the current position matches the next position; whenever the location changes, a new group is created.

### Feature Optimization (continued)

1. Each group does not need to return all photo information; only one photo as a cover plus the photo count for the group is needed.
2. Remove the "trip" type. All timeline items are the same. Keep the `type` field for future extension.
3. Footprint timeline item determination logic:
   1. Use a list to store all timeline items.
   2. Iterate through each photo and check whether the current photo's location matches the previous photo's location.
      1. If a scenic spot exists, use the scenic spot name as the location; otherwise, use the city name.
   3. If the location matches, increment the photo count of the current item by one.
   4. If the location differs, create a new timeline item and add the current photo to the new item's photo list.

---

### Core Visual Optimization

Modify the layout: each item on the timeline vertical line shows a marker. The right side uses a top-bottom layout — date on top, location below, and photos on the far right.

1. **Timeline line redesign**: Replace the thick solid line with a thin soft dashed line / gradient thin line (1px, light gray) to reduce visual prominence. Change nodes to hollow dots (6-8px diameter), lit only where content exists, replacing solid markers. Slightly offset time nodes from the axis to add a journal-style staggered feel, avoiding mechanical alignment.

2. **Information hierarchy simplification**: Time format: "2026.01.17", removing unnecessary symbols. Group title: change "2026 January" to "2026 · 01", weakening hierarchy for a more concise look.

3. **Color system (literary core)**: Background: dark gray to light gray / off-white (lower saturation, simulating paper). Text: pure white to warm gray; time in light blue / light brown, location in dark gray, unified soft tones. Photo area: add slight rounded corners (6-8px), simulating film photo paper texture. No extra high-saturation colors; the overall palette stays within the low-saturation range.

4. **Layout and whitespace (breathing room)**: Increase vertical spacing; line spacing >= 24px to reduce crowding. Photo grid: 2 columns on mobile, 3 columns on PC, each photo with rounded corners + slight shadow. Group collapse: keep the collapse button but change it to a thin-line small arrow for a more refined look.

### Interaction Optimization (Literary Details)

1. **Hover/click effects**: Hover: location text slightly floats up + changes color; photos slightly enlarge; no strong highlighting. Click: expand/collapse with fade-in/fade-out, slower speed, gentler feel. Scroll: timeline nodes fade in and out during page scrolling, simulating the rhythm of turning pages.

2. **Dual-platform adaptation (literary without compromise)**: Mobile: single-column layout, time on the left, photos on the right, overall more spacious. PC: left-right split, timeline on the left, photo stream on the right, ample whitespace. Orientation: in landscape mode, automatically switch to a horizontal timeline, simulating a film reel.
