## Agent Thinking Process and Tool Call Visualization

Currently, the conversation only displays the final result. The waiting time is long with no intermediate process. Thinking process and tool call visualization need to be added to improve user experience.

Add new fields to the `agent_messages` table in `package\server\app\db\models\agent.py` to store thinking process and tool call information.

- reasoning: Thinking text, used to store the agent's thinking process
- tool_calls: JSON-format tool call information, used to store the list of tools called by the agent. Each tool call entry contains the following fields:
  - tool_name: Tool name
  - tool_args: Tool arguments
  - tool_return: Tool return result
  - tool_call_id: Tool call ID, uniquely identifies each tool call
  - tool_status: Tool status, stores the status of the tool call (e.g., success, failure)

`package\server\app\service\agent\service.py` — store thinking content and tool call information to the database.

`package\website\src\views\agent\AgentChat.vue` — add thinking process visualization. Thinking content is displayed in light gray and can be collapsed and expanded. Expand during thinking; collapse after thinking is complete. Tool calls are not displayed in the frontend for now.

## Background Task Management Optimization

The current task management process is started by `main.py` and automatically restarts after a period with no tasks. This needs to be changed so that the process starts only when there are tasks and shuts down when there are none.

Add background task process management functionality to `package\server\app\service\task_manager.py`, including start, stop, and restart operations.

When a user initiates a task (scan folder, retry task, etc.), the background task process should be started. After tasks are complete and a period of time passes with no new tasks, the process should automatically shut down. The task process should no longer run persistently in the background.

# 1. Requirement Overview

This module implements **scheduled incremental scan tasks** for the album. Instead of only a simple minute interval, it supports **3 scheduling modes** with customizable weekly execution days and daily fixed times.

# 2. Complete Scheduled Task Feature (Advanced)

## 2.1 Scheduling Modes (Choose one of three, radio toggle)

The frontend provides radio buttons to switch between 3 modes:
1. **Disable scheduled scan** (no auto-execution, manual only)
2. **Interval loop mode** (execute every N minutes)
3. **Weekly scheduled mode** (execute on specified days of the week at a specified time)

> The separate "daily" mode is dropped: daily = weekly with all 7 days checked, keeping the logic unified and non-redundant.

## 2.2 Detailed Configurable Options per Mode

### Mode A: Interval Loop Scan (preserved from original)
Dropdown-selectable intervals:
5 minutes / 10 minutes / 15 minutes / 30 minutes / 60 minutes

Suitable for: frequent photo updates, desire for quick synchronization.

### Mode B: Weekly Custom Scheduled Scan
Configurable in 3 parts:
1. **Execution days**: Multi-select checkboxes for Monday through Sunday (e.g., only Monday, Wednesday, Sunday)
2. **Execution time**: Hour + minute dropdown selection (HH:mm, e.g., 02:30 for early morning execution)
3. Meaning: Every week on the **checked days**, an incremental scan is automatically executed once at the **fixed time**.

# 3. Frontend Page Complete Interaction Design

## 3.1 Overall Page Layout
1. Scheduled scan master toggle (independent master control)
2. Scheduling mode selection (radio group)
   - Disabled
   - Interval loop scan
   - Weekly scheduled scan
3. Based on the selected mode, **dynamically display the corresponding configuration items** (hide irrelevant configurations)
4. Save configuration button
5. Scan status preview area
6. Scan history log list area

## 3.2 Control Interaction Details

### (1) Scheduling Mode Radio
When switching modes, the form below **instantly switches its displayed content** without requiring saving.

### (2) Interval Mode Panel (displayed when selected)
- Interval dropdown selection: 5/10/15/30/60 minutes
- Hint text: Suitable for frequent uploads; mechanical hard drives may wake up frequently.

### (3) Weekly Scheduled Mode Panel (displayed when selected — this is the key feature you want)
Controls:
1. Day multi-select checkboxes: Sun, Mon, Tue, Wed, Thu, Fri, Sat (7 checkboxes)
   - Supports any combination: Sunday only / Mon-Wed-Fri / Every day (select all)
2. Execution time selector: Hour (0~23) + Minute (0~59) dropdowns
3. Hint text: NAS mechanical hard drives recommended to execute between 02:00~04:00 AM to avoid impacting daily use.

Interactions:
- At least 1 day must be checked; otherwise, saving shows an error "Please select at least one execution day"
- Selecting all 7 days = **execute at a fixed time every day** (satisfying the "daily" requirement)

## 3.4 Save Interaction Logic
1. Modify any configuration -> click [Save Scheduled Settings]
2. Validation: Weekly mode must have at least 1 day checked
3. Save successful: prompt "Scheduled configuration updated, takes effect on the next cycle"
4. Save failed: prompt the specific error reason
5. Configuration is reflected in real-time on the frontend

## 3.5 Disable Logic
- When scheduling is disabled, hide all interval/weekly time configurations
- In weekly mode, hide interval options
- In interval mode, hide day + time options

# 5. Backend Scheduling Rule Description

The backend internally converts everything to Cron expressions:
1. Interval mode -> corresponds to minute-level cron
2. Weekly mode -> day-of-week + time cron
3. Selecting all 7 days weekly = daily fixed time execution
4. Task overlap auto-skip strategy remains unchanged

# 6. Acceptance Criteria
1. Support three modes: disabled, interval loop, and weekly custom day + time
2. Weekly mode supports any multi-select of days; selecting all is equivalent to daily execution
3. Weekly mode requires at least 1 day checked to save
4. Configuration changes take effect on the next scheduled trigger without interrupting the current scan
5. Scheduled tasks that overlap are automatically skipped

# 7. Notes
1. Scheduled tasks should be extensible. Currently used for incremental scan tasks; in the future, other tasks (e.g., AI processing) can be added.
2. The scheduling system and the tasks it triggers must be decoupled. The scheduling system is only responsible for triggering tasks; task execution logic is implemented separately.
3. Scheduled tasks are system configurations, defined in `package\server\app\core\system_config.py`.
4. The scheduled task configuration page is implemented in `package\website\src\views\settings\BasicSettings.vue`.

## Agent Conversation Termination Feature

- In `package\website\src\views\agent\AgentChat.vue`, when the model is outputting, the send button in the input box should change to a "Stop" button. Clicking it interrupts the current conversation — LangChain 1.0 will interrupt communication with the LLM and stop model output.
- After termination, the send button in the input box reverts to "Send". The user can continue entering new instructions. Content already output by the model is preserved.

1. Currently, conversations can be terminated before output starts, but not during output. Termination should be possible at any time before output completes.
2. Although terminated on the frontend, the backend continues outputting content. The backend output should also be stopped, not just hidden on the frontend.

## Recycle Bin Feature

Define the recycle bin scheduled task and expiration period in `package\server\app\core\system_config.py`, defaulting to 7 days expiration and daily cleanup at midnight.

Implement the recycle bin configuration page in `package\website\src\views\settings\BasicSettings.vue`.
Users can configure the expiration period in the recycle bin configuration page, defaulting to 7 days.

Add a deletion flag and deletion time to the `photos` table in `package\server\app\db\models\photo.py` to record when a photo was deleted.

Add a recycle bin button to `package\website\src\views\HomePage.vue`. Clicking it navigates to the recycle bin page.
1. Users can view deleted photos in the recycle bin page and click to restore them.
2. Users can delete photos in the recycle bin page.

## Implement a TrailSnap-cli Tool Skill for Claude Code

The skill includes the following capabilities:

Server API access (write scripts to call the server's API endpoints):

1. Query the photo list based on specified conditions
2. Query tags, albums, locations, people, etc. that exist in the album
3. Query the list of mounted folders

When a user uses the TrailSnap-cli tool for the first time, they need to configure the server's API address and token. Save the configuration information to a configuration file (.env).

The current CLI tool uses a two-level command structure with limited functionality. Now it needs to be expanded to a three-level command structure.

For example:
```bash
python cli.py photos list --city "Xi'an City" --limit 5
python cli.py photos info --photo-id <photo_id>
python cli.py photos delete --photo-id <photo_id>
python cli.py folders list
```

Package and publish the CLI tool.

Core approach (most stable, most popular):
In `package\trailsnap-cli`, compile the Python CLI into standalone binaries (Windows/Mac/Linux can all run directly):
- PyPI package: package binary -> support `pip install`
- npm package: download the corresponding system binary -> support `npm install -g`

Define build and publish workflows in `.github\workflows`, including building and publishing for Windows/Mac/Linux. Commit messages containing "Build CLI tool" trigger the build and publish workflow.
