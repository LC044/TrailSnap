## Duplicate Photo Cleanup Feature

Calculate whether the MD5 values of duplicate photos are the same; if they are, the photos are considered duplicates.

1. `package\website\src\views\toolbox` — add a new duplicate photo cleanup page, similar to `package\website\src\views\toolbox\SimilarPhotoCleanup.vue`.
2. `package\server\app\db\models\photo.py` — add a new field to store the photo's MD5 value.
3. Frontend triggers a "scan duplicate photos" button. Clicking it calls a backend endpoint to create a new task for scanning duplicate photos, similar to scanning similar photos.
   1. The backend scans photos, calculates MD5 values for photos that don't have one, and stores the MD5 values in the photo table.
   2. The frontend can view scan progress. After scanning completes, the duplicate photo list is displayed.
   3. The user can select duplicate photos to delete in the list. Clicking the delete button deletes the selected photos.

## Why

Users' albums may contain a large number of identical photos (e.g., from multiple uploads or backups). By calculating MD5 values, these duplicate photos can be precisely identified, and a cleanup feature can be provided to help users save storage space.

## What Changes

- Add an `md5` field to the backend `Photo` database model for persistently storing the MD5 hash value of photo files.
- Add a new background async task (Task) specifically for scanning photos that have not yet had their MD5 calculated, updating their MD5 values, and then finding groups of duplicate photos with the same MD5 value.
- Provide related API endpoints for triggering the duplicate photo scan task, querying task progress, getting the duplicate photo list, and deleting selected duplicate photos.
- Add a new `DuplicatePhotoCleanup.vue` page in the frontend `package/website/src/views/toolbox` directory (referencing `SimilarPhotoCleanup.vue`), providing a complete user interaction interface.

## Impact

- Affected specs: Storage management, album cleanup tools, task management system

## Task Distribution Optimization

In `package\server\app\service\task_worker.py`, currently the `_fetch_and_dispatch_tasks_sync` function reads tasks from the database, takes a batch to process, and essentially uses the database as a task queue. These tasks can actually be processed concurrently. For example: CPU tasks (building thumbnails, extracting metadata, etc.), IO tasks (face, classify, OCR, etc., where most time is spent waiting for AI microservice responses), AI tasks (also mostly waiting for external LLM output). These tasks can be processed concurrently to improve efficiency.

Therefore, add multiple task queues to `package\server\app\service\task_worker.py`, each responsible for one task type:
1. CPU task queue: handles CPU tasks such as building thumbnails, extracting metadata, etc.
2. IO task queue: handles IO tasks such as face, classify, OCR, etc.
3. AI task queue: handles AI tasks such as `visual_description`, etc.

Task queues use priority queues — higher-priority tasks are processed first.
The `_fetch_and_dispatch_tasks_sync` function takes tasks from these queues and then executes the corresponding strategy class. Therefore, a task queue management module also needs to be added to `package\server\app\service\task_worker.py` to manage these queues.

## Task Batch Processing Optimization

Existing AI microservices all support batch processing to reduce IO requests and improve efficiency. However, the current task processing module processes images one at a time. Consider batch processing to reduce IO requests and improve efficiency. Therefore, each task in these queues can contain multiple subtasks, dispatched to the AI microservice for processing, reducing the number of IO requests and context switches, and improving efficiency.

# Distributed Cache Hot Data Consistency Check Solution

## Overall Approach Analysis

The core of this problem is: **In a distributed cache cluster, the same hot data (e.g., a high-frequency-accessed Key) may be distributed across multiple replica nodes. Due to network latency, node failures, write ordering, etc., data across nodes may become inconsistent.** We need a scaled verification framework to detect such inconsistencies.

## Image Classification Optimization

Currently, a single YOLO model is used for classification. This should be changed to: first use a model for broad classification, then use the corresponding broad-class model for fine classification.

Model files are stored in `package\ai\data\models\photo-cls` directory.
