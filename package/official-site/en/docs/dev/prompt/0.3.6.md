## Agent Chat System Design

### Feature Description

The current chat history is stored in memory and does not support multiple sessions. When the user closes or restarts the application, chat history is lost.

To prevent chat history loss, store chat records in the local database.

### Database Design

The table descriptions below are for reference only. You can modify or add new fields as needed to suit your requirements or for future feature expansion.

1. Sessions table (`agent_sessions`)
   1. id: Session ID, primary key (UUID)
   2. user_id: User ID, foreign key referencing the user table's user_id
   3. created_at: Creation time, records when the session was created
   4. title: Session title, user-customizable
   5. status: Session status, records whether the session has ended
   6. context_summary: Session context summary, records the context summary of the session
   7. summary_update_time: Context summary last update time

2. Messages table
   1. id: Message ID, primary key (auto-increment)
   2. session_id: Session ID, foreign key referencing the sessions table's id
   3. role: Message role — user / assistant / system
   4. content: Message content, records the user's sent message or Agent's reply
   5. content_type: Message content type, e.g. text, image, audio
   6. content_ext: Message content extension, e.g. image URL, audio URL
   7. token_count: Message token count, for billing purposes
   8. created_at: Creation time, records when the message was sent

### Feature Extensions

## New "Token Management" Feature

Feature description: Users can use tokens to call the corresponding user's API endpoints, such as querying the photo list, uploading photos, etc.

New tokens table (`agent_tokens`):
   1. id: Token ID, primary key (UUID)
   2. user_id: User ID, foreign key referencing the user table's user_id
   3. name: Token name, user-customizable
   4. token: Token value, a randomly generated string used to verify user permissions
   5. created_at: Creation time, records when the token was created
   6. expires_at: Expiration time, records when the token expires
   7. is_deleted: Whether deleted, records whether the token has been deleted, default False

Frontend features:
1. `package\website\src\views\settings\Tokens.vue` — new token management page. Users can view all tokens, create new tokens, delete tokens, etc.
2. When creating a token, the user must enter a token name, select an expiration time, and verify their password.
3. When viewing tokens, both the token name and token value are displayed. The user cannot directly view the full token value; they can only copy it. A tag indicates whether the token is expired.

Once a token is deleted, it becomes invalid and can no longer be used to call API endpoints.

## Footprint Timeline Feature

## I. Feature Overview

### 1. Feature Name
Album Footprint Timeline

### 2. Feature Positioning
Automatically generate a visual timeline + geographic trajectory based on photo **capture time + multi-level geographic location (province/city/district/scenic spot/detailed address)**. Support multi-view browsing, filtering, and editing to satisfy users' needs for viewing their life/travel footprints through photos.

### 3. Supported Terminals
PC (web/client) and mobile (phone/tablet), with consistent functionality on both and adaptive layout.

---

## II. Basic Display Rules

### 1. Sorting Rules
1. All photos are displayed in **reverse chronological order by capture time** (newest at the top).
2. Photos taken at the same time and same geographic location are automatically grouped together.
3. Photos without geographic location are not included in the timeline display.

### 2. Geographic Location Display Priority (Fixed Rules)
The feature displays location names according to the following priority, **automatically matched, priority cannot be changed**:
1. First priority: **Scenic spot** (when scenic spot info is available, display: city + scenic spot)
2. Second priority: **District** (when no scenic spot but district is available, display: city + district)
3. Third priority: **City** (when no scenic spot/district, display city only)
4. Fourth priority: **Province/Country** (when no city, display province/country)

### 3. Grouping and Aggregation Rules
1. **Group by day**: Photos taken on the same day are merged into one timeline node by default.
2. **Group by location**: Photos taken on the same day at the same location (scenic spot/district/city) are merged into one footprint point.
3. **Continuous trip aggregation**: When photos are taken in the same city for 3 or more consecutive days, they are automatically aggregated into "XX City - N-day Trip", which can be expanded to view daily details.

---

## IV. Multi-View Display (Universal on Both Platforms)

Provide **2 independent views** that users can freely switch between; view data is fully synchronized.

### View 1: Standard Footprint Timeline (Default View)
1. Vertical timeline layout. The left side displays **time + geographic location**, and the right side displays corresponding photo cover thumbnails. Click to view all photos in the group.
2. Single footprint display format:
   - With scenic spot: `2026-03-25 · Hangzhou City · West Lake Scenic Spot`
   - With district: `2026-03-24 · Beijing City · Chaoyang District`
   - City only: `2026-03-23 · Shanghai City`
3. Collapse/Expand: Support collapsing historical months/years to quickly shrink the view.

### View 2: Map Trajectory View
1. Left: timeline thumbnail list; Right: map panel.
2. The map automatically marks all photo shooting locations and **generates a travel trajectory with connecting lines**.
3. Map marker rules:
   - Marker size: more photos at a location means a larger marker.
   - Click on a marker: automatically display all photos + time + address for that location.
4. Support trajectory show/hide toggle and map fullscreen view.

## III. Dual-Platform Display Adaptation Requirements

### 1. Mobile (Phone/Tablet)
- Standard timeline: single-column photos, vertical scrolling, location info at the top.
- Map view: fullscreen map, photo list pops up from the bottom.
- Immersive view: vertical fullscreen, floating info bar at the bottom.

### 2. PC
- Standard timeline: multi-column photo grid, left side time + location fixed.
- Map view: left-right split, map and timeline displayed on the same screen.

Feature optimizations:
1. Photos are placed on the far right; time and location are vertically centered relative to the photos.
2. The timeline is not necessarily grouped by month. If multiple months are in the same city, all photos for that city are placed in one timeline node.
3. A trip does not necessarily consist of consecutive dates. Even if a day has no photos, but the subsequent photos are still in the same location, they are grouped together. The key is whether the current location differs from the next — whenever the location changes, a new group is created.

Feature optimizations:
1. Each group does not need to return all photo information — only one photo as a cover plus the photo count for the group.
2. Remove the "trip" type. All timeline items are the same; retain the `type` field for future extension.
3. Footprint timeline item determination logic:
   1. Use a list to store all timeline items.
   2. Iterate over each photo and determine whether the current photo's location is the same as the previous photo's location.
      1. If a scenic spot exists, use the scenic spot name as the location; otherwise, use the city name for comparison.
   3. If the same, increment the photo count of the current item.
   4. If different, create a new item and add the current photo to the new item's photo list.

II. Core Visual Optimization
Layout adjustment:
Each item on the timeline's vertical line displays a marker. The right side uses a top-bottom layout: date on top, location below, photos on the far right.

1. Timeline line reconstruction
   Replace the thick solid line with a thin soft dashed line / gradient thin line (1px, light gray) to reduce its visual prominence;
   Change nodes to hollow small dots (6-8px diameter), only lit where there is content, replacing solid markers;
   Time nodes slightly offset from the axis for a hand-drawn, staggered feel, avoiding mechanical alignment.

2. Information hierarchy simplification (reduce complexity)
   Time format: "2026.01.17", removing extra symbols;
   Group title: "2026 Jan" changed to "2026 · 01", weakening hierarchy for a more concise look.

3. Color system (artistic core)
   Background: dark gray to light gray / off-white (reduce saturation, simulate paper);
   Text: pure white to warm gray, time in light blue / light brown, location in dark gray, unified soft tones;
   Photo area: add slight rounded corners (6-8px), simulating the texture of film photo paper;
   No extra high-saturation colors, keeping the overall palette in the low-saturation range.

4. Layout and whitespace (breathing room)
   Increase vertical spacing, row spacing >= 24px, reducing the cramped feel;
   Photo grid: 2 columns on mobile, 3 columns on PC, each photo with rounded corners + slight shadow;
   Group collapse: keep the collapse button but change to a thin-line small arrow for a more refined look.

III. Interaction Optimization (Artistic Details)

1. Hover / Click effects
   Hover: location text slightly floats up + changes color, photos slightly enlarge, no strong highlighting;
   Click: expand / collapse uses fade in/out, speed slowed down for a gentler feel;
   Scroll: timeline nodes fade in and out during page scrolling, simulating the rhythm of turning a book page.

2. Dual-platform adaptation (artistry without compromise)
   Mobile: single-column layout, time on the left, photos on the right, overall more spacious;
   PC: left-right split, timeline on the left, photo stream on the right, ample whitespace;
   Landscape/portrait: in landscape orientation, automatically switch to horizontal timeline, simulating a film reel.
